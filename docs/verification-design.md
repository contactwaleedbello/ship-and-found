## 1. Cryptographic Generation vs. Predictable Pseudorandomness

Our email verification codes are strictly generated using the platform cryptographic pseudo-random number generator (CSPRNG) via `crypto.randomInt(100000, 1000000)`.

### Why Standard `Math.random()` Fails Critically:
Standard `Math.random()` in JavaScript engines (V8, JavaScriptCore) relies on algorithms like **xorshift128+**. These are pseudorandom number generators designed for speed and graphical simulations, not security:
- `xorshift128+` maintains an internal 128-bit state.
- By observing just **two or three consecutive 6-digit codes** generated by `Math.random()`, an attacker can mathematically reconstruct the internal PRNG state via Z3 solver algorithms.
- Once the internal state is known, the attacker accurately predicts all future verification codes for any user registering on the platform before the email even arrives.

### What an Attacker Could Do Against Predictable Codes:
> If verification codes were generated using `Math.random()`, an attacker registering two burner accounts at 12:00:00 and 12:00:05 would observe codes `481902` and `891234`. Reconstructing the internal state generator, they calculate that the very next code issued at 12:00:10 to `victim.customer@gmail.com` will be `314159`. The attacker skips reading the victim's email entirely, sends `POST /api/auth/verify-otp` with `314159`, and takes over the victim's registration session. Given our 10-minute validity window, the attacker has 600 seconds to execute this prediction without triggering our 5-attempt rate limit.
>
> Using `crypto.randomInt` draws entropy from the operating system kernel CSPRNG (`/dev/urandom` / hardware entropy pool), making successive outputs completely uncorrelated and mathematically unpredictable.

## 2. Expiry Window Justification: Why 10 Minutes is Chosen

In class, an initial 2-minute expiration window was rejected as unworkable for real humans. We established a **10-minute expiration window** (`OTP_CONFIG.EXPIRY_MS = 10 * 60 * 1000`).

### The Two Evaluated Dimensions:
1. **How Long Real Users Actually Need**:
   - In Nigeria, customers sign up on mobile browsers while navigating congested commercial plazas (Banex Plaza, Wuse 2).
   - Switching applications, waiting for local cellular network handshakes (MTN/Airtel latency spikes), navigating biometric app locks on email clients, and waiting for Gmail push notifications regularly takes **3 to 6 minutes**.
   - A 2-minute window causes constant timeouts, frustration, and abandoned checkouts. 10 minutes gives legitimate human customers ample time to retrieve and enter their code.
2. **The Cost in Attack Surface**:
   - Expanding the window from 2 minutes to 10 minutes expands the time window during which an attacker could attempt a brute-force attack.
   - However, our code space contains $900,000$ possible 6-digit codes ($100000$ to $999999$).
   - Crucially, our endpoint enforces **maximum 3 attempts per code** (`OTP_CONFIG.MAX_ATTEMPTS = 3`).
   - The probability of an attacker guessing the code in 3 attempts across 10 minutes is:
     $$P(\text{Breach}) = \frac{3}{900,000} = 0.000333\% \approx \mathbf{1\text{ in }300,000}$$
   - Because strict attempt limits neutralize brute-force attacks, the 10-minute window provides optimal user ergonomics with zero compromise to cryptographic security.

## 3. Replay Attack & Code Reuse Defect Defense

During development of Task 4, we identified defect `DEF-T4-03`: an email verification code remained valid after successful verification until its natural 10-minute timer expired.

### The Attack Vector:
1. Customer Ahmed registers with code `749201`.
2. Ahmed verifies his account successfully (`HTTP 200 OK`).
3. An adversary eavesdropping on public Wi-Fi or with temporary access to Ahmed's phone enters the same code `749201` again in a password reset or re-verification flow. Because the code was not expired, the server re-accepted it.

### The Architectural Fix (Atomic Consumption):
In `lib/security/otp-service.ts`, we introduced an explicit `consumedAt: number | null` field:
```ts
if (record.consumedAt !== null) {
  return {
    status: 'ALREADY_USED',
    message: 'This verification code has already been consumed. Request a new code.',
  };
}
// Upon successful verification:
record.consumedAt = Date.now();
```
As verified in `evidence/22-verification-code-reused.png`, repeating the request with an already-used code immediately returns **`HTTP 409 Conflict: Code Already Consumed`**, eliminating the replay vulnerability completely.
